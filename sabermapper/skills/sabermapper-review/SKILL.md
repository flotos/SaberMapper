# Review a map

Read the exact arrangement, compiled map or ZIP, audio hash, diagnostics, review notes, and requested scope. A project can hold several difficulties. Find the one the feedback is about (feedback records carry `difficulty`) and pass `--difficulty NAME` to `project get`, `save`, `check` and `music rhythm`. When feedback says a map is too easy or too hard, move its `difficulty.target_tier` by one tier. You can also add a difficulty at the new tier and keep the old one. Then use the `tier_fit` critique; see the map skill's [difficulties and star tiers](../sabermapper-map/references/difficulties.md). If the user reports a problem, reproduce it in the file and identify a beat range and section. Read [review rubric](references/rubric.md) for the defect versus taste distinction.

Run `python -m sabermapper project check ID --workspace workspace` (or `validate ARRANGEMENT.json` for a standalone file) and inspect blocking findings before evaluating flow. Compare notes with the checked audio grid and phrase intent. Assess both hands through entry, motion and exit; inspect sight lines, density, rests, repeated sections, obstacles, lights, and NJS in context. Repeated sections should sound and play alike: `repeat_unechoed` marks a part of the song that repeats an earlier one (listen repetition group or the stems' rhythm) but is mapped as an unrelated pattern. Its `add_theme` suggestion declares the theme and reopens the echo notes so the placer echoes the earlier placement. `theme_unechoed` marks a declared echo that pins or stored values keep from following. Rename a suggested theme after the sound it carries. A movement warning is a prompt for review, not automatic permission to alter the pattern. Flow errors are different; they are a standing player rule. `fast_direction_break` fires when a same-hand cut 0.3 s or less after the previous one turns less than 135 degrees. `flow_parity_break` fires when consecutive same-hand swings turn less than 90 degrees or stay on the same forehand/backhand. The only exemption is a rest of 2 s or more on that hand; a full beat is not a reset. Every cut starts where the previous one left the saber (standing rule after Borrowed Waters, 2026-09-23). `one_hand_burst` (warning) marks three or more same-hand cuts, each under 0.2 s after the last, while the other hand idles. `hidden_note` is the sight-line rule: a note arriving in the same cell as the note just in front of it, less than 0.35 s later in the centre middle/top cells or 0.2 s later elsewhere. The placer keeps all of these by construction for every field it chooses, so a finding means a pinned choice or a hand-written map. Fix it with the finding's verified `suggestions` (a new cut, hand or cell), or unpin the fields and let the placer choose. When a player reports an awkward swing pair or a hidden note, generalize it rather than patching one spot. Reproduce the pair and check whether the model flags it. If it does not, extend `movement.flow_break` or `movement.hidden_note` and its tests; the placer and `project check` then follow on every project, and `project check` on each one shows where the rule now fires.

Audio is the focus of every review. Run `python -m sabermapper project check ID --workspace workspace`; it uses the project's newest evidence run for the current audio. Treat `audio_unmapped` (the song plays but the map is empty, blocking from 8 s), `note_without_audio` and `low_audio_support` (notes with no sound under them) as defects to fix before judging patterns or flow. `audio_evidence_missing` means the map was never checked against the song; run `music analyze` first. `vocal_line_unmapped` and `drum_rhythm_unmapped` mean the notes miss the bar's salient layer (articulated singing, else the drum pattern while the voice holds). `melody_unmapped` means no voice, drums or declared lead carry the bars and the notes miss the pitched line's `melody_change` events; follow "Follow the melody" in the map skill's musical focus reference. `drum_entry_unmapped` means the drums arrive after a break and the map ignores them; `ensemble_unmapped` means the notes follow the lead alone and skip every heavy hit of the rest of the band. `focus_on_quiet_stem` means a focus phrase weights a stem that is absent there, as bleed or a mislabeled instrument. `difficulty_exceeds_intensity` (a soft bar as hard as the heavy passages) and `intensity_underplayed` (a heavy run easier than the soft passages) mean difficulty does not follow loudness; when a player says a map gets easier as the music gets heavier, read `metrics.intensity.bars` for the exact bars. These appear in `project get`/`project save` diagnostics as warnings; resolve or justify each. Each finding carries `suggestions`: the edit that addresses it, drawn from the same rules as `music rhythm --propose` (add notes on the sounds it names, retime or remove notes off every sound, remove stray times that bury the lead, thin a quiet passage or a soft bar, raise a heavy run, set new focus weights). To re-author a flagged passage, draft it with `music rhythm ID --workspace workspace --propose --start A --end B --draft DRAFT.json`, edit the draft, check it with `project check ID --workspace workspace --arrangement DRAFT.json`, and save it. Apply a fix to every project where the finding appears, and review what the draft reports under `remaining`.

For musical connection, inspect section `musical_focus` annotations and exact
`musical/RUN_ID/report.json` evidence. `python -m sabermapper music rhythm ID --workspace workspace --start A --end B`
prints per-bar attack grids per layer beside the mapped notes; use it when feedback says the pacing is regular or
misses an instrument. `python -m sabermapper music spectrogram ID --workspace workspace --start A --end B` writes a
PNG of the mix and every stem over that range with the notes, attacks and stem entries; read it before and after
revising a passage, and read the run's `overview.png` for the whole song. `python -m sabermapper music inspect ID
--workspace workspace --run RUN_ID --start BEAT --end BEAT` converts source events
to the current grid, including tempo changes. Check the declared lead's rhythm,
rests, intentional handoffs and ensemble accents against actual notes. Missing
layers, separator bleed and detector peaks are uncertainty, not proof of an
instrument event. Weights express agent intent, not automatic note generation.
Focus metadata is revision-aware and locked with its containing section.

Lighting feedback ("too flashy in the verse", "the drop needs more", "lights ignore the guitar") is revised through `arrangement.lightshow`, never by editing its `generated` events. Read the map skill's [lightshow reference](../sabermapper-map/references/lightshow.md), locate the moment with `python -m sabermapper project lights-inspect ID --workspace workspace --start A --end B`, then change a section override (mood, primary, boost, white_accents, intensity) or add cues (pulse, off, spin, zoom, laser_speed, boost, event, clear), and save; the generated layer rebuilds around them. Treat `light_strobe` (blocking), `light_flash_heavy`, `light_unmapped`, `light_without_audio`, `light_blackout_notes`, `light_density` and `lightshow_stale` like the audio findings. When a lighting complaint is general (for example lasers never follow the guitar), fix the generator in `sabermapper/lighting.py` with a test and regenerate every project with `project lights`, rather than cueing one song.

For a scoped edit, preserve locked sections and unrelated data. Save a new arrangement, compile to a new path, and compare object counts and the exact changed beat range. Export only if resolved and provided with a decodable local OGG Vorbis and valid cover. Do not open ArcViewer, the studio or a browser preview unless the user asks; the user reviews saved revisions themselves, and a rendered view the agent cannot see is not a check. Only an actual user game playtest establishes feel and replay desire. State which stages were completed and what remains unverified.
