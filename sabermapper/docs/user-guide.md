# Use SaberMapper locally

SaberMapper works on local files. An independently invoked assistant can author the JSON arrangement; the Python program does not contact an LLM. Start in the project directory and use the environment created by the setup script, or activate `.venv` and run `python -m sabermapper --help` to see the commands in your installed version. On Windows PowerShell, `./.venv/Scripts/python` can replace `python` below.

## Try the original demo

The generated 48-second demonstration is original synthesized audio with three progressively fuller sections. It is useful for checking the local workflow without obtaining a song or cover. Run `python -m sabermapper demo --workspace workspace`; it creates a saved local project and prints its ID. `python -m sabermapper project get ID --workspace workspace` inspects it. The demo demonstrates software integration, not whether the player enjoys the generated map.

## Prepare a real song

Choose a locally available WAV, FLAC, OGG or MP3 that you can use for this purpose. Record the source path and SHA-256, manually enter title and artist, and inspect decoded duration and waveform. `sabermapper.audio.inspect_audio(path)` returns a local identity record without guessing tags from the filename. `analyze_audio(path, bpm=..., offset_seconds=...)` provides onset, energy, tempo and section candidates. Review BPM, beat-zero phase and a bar anchor against the exact audio near its start, middle and end. The proposed half/double tempo alternatives are prompts to listen, not verified answers. Encode a new Vorbis file with `prepare_audio(source, destination)` if needed; it records both hashes and checks decoded duration/onset shift. Retain the original audio and conversion record.

The CLI can create a real project with `python -m sabermapper import-audio TRACK --workspace workspace --title TITLE --artist ARTIST --bpm BPM`; title/artist may be entered later. Importing audio whose exact source bytes already belong to a project is refused with the existing project ID (continue that project instead); pass `--allow-duplicate` only for a deliberate second copy. Mis-encoded title/artist text such as `FumÃ©e` is repaired to UTF-8 on import. The studio sidebar groups projects as artist / album / song, alphabetically, with each song's last-update time (month/day hh:mm); the album comes from `--album`, else the file's album tag, else an `Artist/Album/` source folder. Change it later with `python -m sabermapper project set-album ID --workspace workspace --album NAME` (an empty name restores the derived album). For an analysis JSON without creating a project, run `python -m sabermapper analyze TRACK --bpm BPM --offset SECONDS --output report.json`. Use `python -m sabermapper serve --workspace workspace --port 8765` for the local browser review UI, then browse the displayed localhost address. The running studio follows code updates: when files in the `sabermapper` package change (an agent merged into `main`), it checks that the new code compiles and imports, waits until no request is in flight, and restarts its server process on the same port and session token. Open pages keep working and show a "reload when ready" banner; they never reload themselves, and ArcViewer tabs are unaffected. An update that fails the check is not loaded and the banner says so. `GET /api/status` reports `code` (`version`, `commit`, `started_at`, `update.state` of `current`, `pending` or `failed` with `error`). `serve --no-reload` keeps the code loaded at start. The UI is a 2D review surface and does not replace editor or game playback. The **Map idea** panel shows the map's style and its summary paragraph (the mapping goal and approach). Each section card shows a one-sentence summary with the agent's evidence folded under *Evidence*; clicking a card opens the SaberMapper viewer at that section. The viewer (`/viewer/`, also opened by **3D preview**) shows ArcViewer in the middle, the style and the current section's summary on the left, and every section top to bottom on the right. Each folded row (name, start time, theme dots) jumps there when clicked, reloading ArcViewer at that point; the current section unfolds to its summary, themes and progress and follows ArcViewer while the song plays. `project outline ID` prints the same texts and time ranges for agents. Projects keep arrangement revisions, locks and feedback in the selected workspace. Back up that workspace along with exact source audio and art.

## Author, validate and export

For instrument-led phrasing and whole-mix accents, the agent uses `music backends`,
`music analyze` (recommended: `--backend ensemble`; `--from-run RUN_ID` re-analyzes existing stems), `music list`,
`music inspect`, `music rhythm` (per-bar attack grids per layer beside the mapped notes) and `music spectrogram`
(a PNG of the mix and stems over a beat range with the notes; each run also writes `overview.png`). The studio's **Music layers**
panel is an optional agent-operated inspection surface. See [musical analysis and agent composition](musical-analysis.md)
for separation options, phrase focus weights, and listening controls. Codex or
Claude Code authors the rhythms and movements from this evidence.

The arrangement schema is summarized in the bundled [map skill](../skills/sabermapper-map/SKILL.md). It names song BPM/offset, one difficulty, reusable motifs, and ordered sections with stable IDs. A section can be marked unresolved while timing or its transition is uncertain; compilation will then fail until it is reviewed. Keep locked sections intact during an assistant edit.

```powershell
python -m sabermapper validate arrangement.json
python -m sabermapper compile arrangement.json --output Expert.dat
python -m sabermapper export arrangement.json --audio track.ogg --cover cover.png --output map.zip
```

`validate` prints JSON diagnostics and exits nonzero for hard errors. `compile` writes Beat Saber v3.3 difficulty data. `export` writes a ZIP with Info.dat, the difficulty, song audio, cover and `SaberMapper-report.json`. Each output path must be new. Audio must decode as OGG Vorbis and the final gameplay object must fit inside decoded duration. PNG or JPEG covers are accepted. A positive `audio_offset_seconds` shifts exported object beats while Info.dat stays at zero offset. It does not edit the source audio. Keep the compatibility report and exact ZIP hash with your project record.

Arcs and chains must be connected. `validate` reports a hard error when an arc has no color note at its head or tail, or a chain none at its head, matching the same beat, lane, row, colour and cut direction (`arc_head_without_note`, `arc_tail_without_note`, `chain_head_without_note`, plus `*_direction_mismatch` when a note is there with a different direction). An unconnected arc would export as a cosmetic curve rather than a held note.

For a scoped change, give the assistant the report, relevant reviewed phrases, the current arrangement, and the player's beat-ranged feedback. Save a new arrangement/ZIP and compare the changed section while preserving unrelated sections and locks. The [review skill](../skills/sabermapper-review/SKILL.md) has a defect-versus-taste rubric. Use the [research skill](../skills/sabermapper-research/SKILL.md) only when collecting external mapping references or phrases.

A project can hold several difficulties. `project add-difficulty ID --workspace workspace --name ExpertPlus --target-tier challenge` adds one as an unlocked copy of the primary difficulty, to be rewritten at its own level. Every project command takes `--difficulty NAME`; without it, commands act on the primary difficulty (`arrangement.json`), and `project export` writes all difficulties into one ZIP. `difficulty.target_tier` names a player star tier: `below_band` <6.5, `band` 6.5–8, `challenge` 8–9, `stretch` up to the hardest recorded pass, `beyond`. `project critique` compares the map's 4-beat windows with real charts of each tier (`metrics.tier_fit`). `corpus tiers` shows each tier's reference metrics, and `corpus retrieve --tier TIER` finds phrases from charts of that tier. The studio's difficulty menu switches the difficulty being reviewed.

For a saved project, get its current revision with `project get ID --workspace workspace`, then save an edited JSON file with `project save ID --workspace workspace --revision CURRENT_SHA --arrangement EDITED.json`. `project export ID --workspace workspace` creates a ZIP with a new filename. `feedback ID --workspace workspace --start BEAT --end BEAT --text "..." --revision CURRENT_SHA` records a beat-ranged instruction for the assistant. After a real playtest, `project review ID --workspace workspace --revision CURRENT_SHA --playtested --game-build BUILD --notes "..." --minutes NUMBER --decision revise` records the observation. A `go` decision requires an actual recorded game playtest; do not mark an automated QA observation as user feedback.

`project check ID --workspace workspace` is the one read-only report of everything the map breaks or misses. It merges placement, structural validation, the movement model, audio grounding against the newest musical evidence run, and the critique. Every finding carries `code`, `severity`, `blocking`, `source`, `beats`, `object_ids`, `message` and `suggestions`. Suggestions are concrete edits: `set` a cut or hand, `move` to a cell, `retime`, `remove`, `add` rhythm-only notes on the sounds a finding names, `unpin` a field so the placer chooses it, `set_weights` for a focus phrase, or `stack` to turn a unison hit's note into a stack. Each suggestion for a blocking movement finding is verified to clear it. `project save` refuses exactly the findings the report marks `blocking`. `--arrangement DRAFT.json` checks a draft as save would place it, and writes nothing. `project critique` is kept as an alias of `project check --metrics`, and top-level `validate` and `critique` run the same report on a standalone file.

Notes need only `id` and `beat`: the placer chooses each note's hand, cut and cell so the flow, held-saber, burst, reach and sight-line rules hold. Any field you write is a pin that placement never changes. `music rhythm ID --workspace workspace --propose [--start A --end B] [--draft DRAFT.json]` drafts the note times themselves from the critique's own rules, bar by bar. Each bar gets one role from the evidence. A soft bar maps melody and chord changes half a beat apart. Every drafted time stays within 35 ms of its sound: the coarsest grid that reaches it, else its own time, so a free-time choir is not pulled onto a grid it does not follow (`note_off_sound` reports notes 40 ms or more off their sounds: three of six in a row, or any one where no drum plays). A riff bar follows the riff's attacks with the kick on the sixteenth grid, but not between two chugs. A sung bar follows the syllables, with the band in the voice's gaps and on the free hand under held arcs. Held and intense singing becomes an arc, and so does a hold the player named (`held_vocals` in `player-profile.json`, or `--held SECONDS`). Doubles mark a loud bar's heaviest accents, and both hands reach them on one parity. Stacks mark its unison hits, where the drums and two more instruments strike together on one of the song's loudest attacks: notes marked `"stack": true` at one beat, two, or three on the rarer hits where four instruments join on one of the song's loudest 5% of attacks, that the placer gives one hand and one cut in a line along it (a stack of three vertical or diagonal, never sideways), a diagonal when the flow allows. A stack never hides the notes after it, stays to the side when notes follow quickly, and the other hand never touches it; no cut anywhere sweeps through a note of the other color at the same instant (`cut_path_blocked`). `project check` reports a unison hit cut without one as `unison_hit_unstacked`, with a `stack` suggestion. The difficulty's target tier and each bar's loudness cap how many note times it carries. The draft is placed and critiqued until no `note_without_audio`, `density_exceeds_audio`, `lead_rhythm_*`, intensity or `one_hand_burst` finding remains. Anything left over is listed under `remaining`. Each drafted time names the sound under it. Edit the draft, then save it.

Every saved project also gets an audio-driven lightshow. When a musical evidence run exists, `project save` generates one if the arrangement has none, and regenerates it whenever the evidence, timing, sections or lighting inputs change. Drums pulse the back lasers, center and rings, the lead instrument drives the side lasers and their speed, chord changes swap colors, and section energy sets calm, groove or peak moods. Export writes the events and the chosen environment. `project lights ID --workspace workspace --revision CURRENT_SHA [--dry-run]` rebuilds it on demand. `project lights-inspect ID --workspace workspace --start BEAT --end BEAT` lists every lighting moment with the sounds under it. The agent tweaks the show through `lightshow.sections` overrides and `lightshow.cues`, as described in the [lightshow reference](../skills/sabermapper-map/references/lightshow.md). Strobing (more than 8 full-field pulses per second) blocks saving. The other lighting checks appear as warnings in `project get` and `project critique`. The density targets come from `scripts/lighting_reference.py`, which measured 132 lit reference maps and stores the results in `sabermapper/resources/lighting-reference.json`.

To make the bundled skills discoverable in Codex from this repository, run `python scripts/install_skills.py`. It copies all three complete directories into workspace-root `.agents/skills/` for Codex and `.claude/skills/` for Claude. Root `AGENTS.md` and `CLAUDE.md` provide the shared project overview. Use `--update` to refresh existing copies after edits. You can then invoke `$sabermapper-map`, `$sabermapper-research`, or `$sabermapper-review` explicitly. Codex's [official skill documentation](https://developers.openai.com/es-419/docs/build-skills) describes repository and user discovery locations; restart Codex if a newly copied skill is not shown.

Vivified maps add a project-level `show.json`, which is independent of difficulty, and optional arrangement 0.2 `presentation` blocks. The agent saves the show with `show save ID --workspace workspace --show show.json --revision CURRENT` (`none` for the first save). It checks the show with `show validate ID` and inspects the merged events and their audio provenance with `show compile ID`. The bundle set (`bundleinfo.json` plus `bundle*.vivify`) lives in `<project>/assets/`. `project export` then also writes a `-vanilla.zip` twin for ArcViewer and a `.show.json` provenance sidecar. See [vivify-show.md](vivify-show.md).

Before the show, the agent listens and writes a concept. `music listen ID` stores sections, moments (drops, builds, breaks, key changes, final chorus and more) and per-section mood in the evidence run. `music lyrics ID` adds word-timed lyrics from Whisper, or from `--from-file` with an LRC or text sheet. `concept template|validate|save|get ID` holds three scored treatments with one selected. See [listen-and-concept.md](listen-and-concept.md).

## Verify in the game and leave notes

The studio's **Verify in game** panel is the human's whole verification job, in four actions: pick a revision, press **Play in game** (map start) or **Play at playhead** (or **Watch** for an autoplay run), scrub with the song-time slider, and press **Note** (or the `N` key) to leave a comment at the current song time. Everything else is agent work.

- **Revision picker**: the current revision and the saved history of the difficulty shown. Play and Note apply to the picked revision.
- **Lease indicator**: who is using the game (free, you, or an agent with its purpose). If an agent holds the game, Play first asks "An agent (holder, purpose) is using the game. Continue?"; continuing revokes the agent's lease, and its capture fails with `game_preempted` and retries later. The human always wins.
- **Slider**: dragging seeks the game after a 300 ms pause (a restart at that time when exact seek is impossible); while the game plays, the slider follows the game's song time (polled every 0.4 s only while the console is visible and the game runs). When the game is not running, the slider is the studio playhead. Section starts (lines), key moments (diamonds, when the project has a `moments` list) and this revision's notes (dots) sit under the slider; click a note to jump there.
- **Watch** reports "not available yet" until ghost autoplay (ticket M6) exists.

Each note stores `{kind: "note", project, revision, difficulty, song_time, beat, section, section_label, text, created_at, source}` in the project's `feedback/` folder next to the beat-range feedback. The beat is computed from the song time with the song BPM, `audio_offset_seconds` and `tempo_events` of the reviewed revision, and `section` is the ID of the arrangement section containing that beat (`section_label` is its label, name or intent). A note on an older saved revision is accepted and marked `stale: true` with both `revision` and `current_revision`, because the human may verify an earlier version; a revision that was never saved for that difficulty is refused. Times must lie within the song and text must be 1–2,000 characters.

The agent reads the notes with `project feedback list ID --workspace workspace [--difficulty D] [--revision SHA_OR_PREFIX] [--kind note|range] [--since ISO]`. It returns notes and beat ranges from every difficulty (unless filtered), sorted by song time, each with `beat`, `section`, `revision` and `on_current_revision`. `project feedback add ID --workspace workspace --at SECONDS --text TEXT [--revision SHA] [--difficulty D]` is the CLI twin of the Note button. Once a saved revision answers a record, `project feedback resolve ID FEEDBACK_ID --workspace workspace --note HOW [--revision SHA]` marks it `addressed` with that revision (default: the current one of its difficulty) and the note, even when the record was written on an older revision. Every studio control has an HTTP endpoint the agent can call too: `GET /api/game/status`, `POST /api/game/play` (`{project, revision, difficulty, seconds, mode: "play"|"watch", confirm_preempt}`), `POST /api/game/{pause,resume,restart,seek,stop}`, `POST /api/projects/ID/note` and `GET /api/projects/ID/feedback`. Game errors are `{"error": {"code", "message", "details", "fix"}}`: 409 for `game_busy`, `game_preempted`, `lease_not_held`, `game_not_running` and `stale_revision`, 503 for `bridge_missing` (the game integration is not installed) and `bridge_unreachable`. The game transport CLI lives under `sabermapper game ...`.

The agent's twins run through the SaberMapper Bridge mod (`Plugins/SaberMapperBridge.dll`, built with `sabermapper game build-bridge --install`): `game launch`, `game status`, `game play ID --at S`, `game seek S`, `game pause`, `game resume`, `game restart`, `game stop`, `game close`, `game install ID` and the self-contained `game capture ID` (leased FPFC run that writes PNG frames and `capture.json` into `<project>/captures/`, then closes the game it opened). Seeking is a restart at that time; Heck/Vivify maps are captured from song time 0 because late starts do not rebuild their animation state. API, launch method and the M0 findings: [game-bridge.md](game-bridge.md).

Before a revision reaches the human, the agent runs the handover gate, `project verify ID --workspace workspace [--difficulty D] [--capture DIR] [--record]`. It checks structure (validation errors), audio (unresolved `audio_unmapped`, `note_without_audio`, `note_off_sound`, `low_audio_support` or missing evidence), the Vivify show (when the project has one), and the newest in-game capture of exactly this revision: frame metrics (a flash rate above 3 per second blocks; a vivified map must include a dense probe so that check ran) and the game-log errors stored in `capture.json`. A capture is required for a vivified project and optional otherwise. The result lists `ran`, `skipped` (with reasons), `blocking` findings and `next` steps; `ready_for_human` is true (exit code 0) only when nothing blocks, else the exit code is 3. `--record` stores it in `<project>/verifications/`. The whole agent loop for vivified maps is the `sabermapper-vivify` skill.

## Inspect and playtest

Preview the ZIP in a compatible editor or ArcViewer, then import it into the exact Beat Saber build you intend to use. Check the opening, middle and ending against audio, note visibility, movement, lighting, and the player's comfort. Record game/editor version, mods, artifacts, editing time, problems and whether the player wants to replay the map. Make one scoped revision and repeat the playtest. A successful validator or ZIP export is not evidence of in-game compatibility or enjoyment. [The evaluation protocol](evaluation-protocol.md) gives a compact comparison record.

## Map work in git worktrees

The real workspace is `sabermapper/workspace/` in the main checkout: user data, shared by the studio and every agent through one `.project.lock`. An agent working in a git worktree maps against its own copy instead:

- `workspace clone [--workspace workspace] [--from REAL] [--skip-corpus]` copies the real workspace (found through the repository's main checkout) into the worktree's `sabermapper/workspace/`. Audio and content-addressed files never change after they are written, so they are hardlinked and take no extra space; every other file is copied, so in-place writers (SQLite, logs) only touch the clone. Project exports and downloader state are left out. `.clone.json` records the size and modification time of every cloned file. `--skip-corpus` keeps only the corpus files project commands read.
- Every command with `--workspace workspace` then works on the clone and never waits on another process.
- After the code is merged into `main`, `workspace status` lists, per unit (a project, an authoring folder, the corpus, the profile), the files changed in the clone and whether the real workspace changed since the clone. `workspace publish [UNIT ...] [--dry-run]` copies only the changed, added and deleted files into the real workspace, under its lock, with the arrangement files last. It holds back a unit where the real workspace changed a file the clone also changed: exit code 2, the conflicting paths, and the `project save` against the real workspace that reapplies the change. Publishing is idempotent.
- `workspace clone --replace` starts again from the real workspace; it refuses while changes are unpublished unless `--discard-local` is given.

## Corpus and learning tools

The local corpus path can import a map ZIP, fetch an exact BeatSaver version when requested, parse maps, group/retrieve phrases, freeze song-family splits and store human preference labels. Use `python -m sabermapper corpus status --workspace workspace` to see the local store. `corpus import ARCHIVE --hash VERSION_HASH --workspace workspace` imports a local archive; `corpus fetch VERSION_HASH --workspace workspace` explicitly fetches an exact BeatSaver version; `corpus process --workspace workspace` extracts patterns; and `corpus retrieve --workspace workspace --bpm 120 --nps 4.5 --limit 20` lists nearby phrases. `corpus batch SEEDS.json` applies the stated budget in the seed file; `corpus cleanup VERSION_HASH` removes a retained archive after processing. Use `--help` on each leaf before a broader run.

For local evaluation records, `profile calibrate SNAPSHOT.json`, `profile feedback RECORD.json`, `splits freeze RECORDS.json --output FROZEN.json`, and `labels add RECORD.json` record provenance and grouping. `labels report` summarizes the stored labels; `labels train --dimension DIMENSION` trains only if its held-out checks and minimum sample gates pass. `parse-map MAP --bpm BPM --output IR.json` normalizes a supported v2/v3 map. These research steps do not automatically author a full map. Use exact source provenance and keep third-party audio and map rights visible. A small local ranker is optional and should only be used after held-out evaluation. Its scores are not a substitute for the intended player's review.

The current [feature list](supported-features.md) distinguishes implemented local behavior from unresolved game and user checks. The project performs no automatic publishing or audio redistribution.

The original demo ZIP and a separate [assistant-authored study](authored-study.md) were loaded in ArcViewer's browser preview. Their screenshots and exact ZIP hashes document preview import only; the intended player's VR playtest remains open.
